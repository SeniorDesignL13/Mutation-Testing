# 13. Data and Database Design

## 13.1 Role of Data

MTLJ does not train a model, and nothing in the system learns from data. Data plays a different role: it is the known-good starting point that ground truth is built from. Every result depends on the original answers being correct before an operator touches them, because breaking an answer that was already wrong says nothing about the judge. Choosing the corpus was therefore the first real research task.

## 13.2 Choosing a Corpus

The team compared four public datasets (MTLJ-40) on size, license, answer format, and whether the provided context actually determines whether an answer is faithful. Sample records from the top two were checked by hand. {tab:datasets} summarizes the comparison.

Table: Candidate datasets {#datasets}
| Dataset | Answers | Context | Verdict |
|---|---|---|---|
| RAGTruth {ref:ragtruth} | About seven sentences each | About 1,200 characters, with human hallucination labels | Selected |
| HaluEval {ref:halueval} | Short spans | About 320 characters | Answers too short to pad or reformat |
| HotpotQA {ref:hotpotqa} | Short extracted spans | Multi-hop Wikipedia paragraphs | No model answers to edit |
| FEVER {ref:fever} | Claims, not answers | Wikipedia evidence | Different task |

Answer length decided it. A two-word answer cannot be padded or reformatted, so with HaluEval half of the MVP operators would have had nothing to work with. Longer answers also give finer scores. Faithfulness is a fraction of supported claims, so a four-claim answer can only score 0, 0.25, 0.5, 0.75, or 1, while a seven-sentence answer has many more steps.

RAGTruth is MIT-licensed and has about 18,000 annotated responses. Each has a question, source passages, a model's answer, and human labels marking exactly which spans are unsupported or contradicted. Its question-answering portion is built on MS MARCO {ref:msmarco}. One of its label types, "evident conflict," is exactly what entity substitution produces, appearing naturally in real model output. That helps answer the obvious objection that scripted edits might not resemble real mistakes.

## 13.3 Filtering and Freezing

{tab:filter} shows the filter chain, which `scripts/freeze_corpus.py` reproduces exactly.

Table: Corpus v1 filter chain {#filter}
| Step | Records remaining |
|---|---|
| All RAGTruth records (train and test) | 17,790 |
| Question-answering task only | 5,934 |
| No hallucination annotation | 4,210 |
| Generated by GPT-4 (gpt-4-0613) | 947 |
| Rated good quality (drops 27 incorrect refusals and 1 truncated answer) | 919 |
| Non-empty question, answer, and context | 919 |

The team kept only GPT-4's answers because GPT-4 had the lowest hallucination rate in the benchmark (4.4%, against 51.2% for Llama-2-7B), which gives the cleanest pool and removes the generating model as a confound. Along the way the team found and fixed a bug in which hallucination fields counted as true whenever they existed, whatever their value. It was caught only by inspecting records by hand.

The final 919 records were frozen as corpus v1 (MTLJ-44) with a SHA-256 checksum and a manifest recording the filter chain and composition. Records are sorted by ID before writing, so rerunning the script gives a byte-identical file. A new corpus always gets a new version directory; `corpus/v1/` is never edited in place. {tab:composition} describes the corpus.

Table: Corpus v1 composition {#composition}
| Property | Value |
|---|---|
| Records | 919 |
| Median answer length | 99 words |
| Answer length range | 7 to 237 words |
| Median context length | 1,213 characters |
| Passages per record | 3 |
| Gold set (hand-checked during the feasibility study) | 20 records |

The corpus has known limitations, recorded so findings are not over-generalized. MS MARCO questions are everyday web searches (cooking, home repair, consumer health), so findings may not transfer to technical, legal, or clinical text. A single generating model means a narrower range of answer styles. And "clean" is not uncontested: the feasibility study found the judge flagging at least one claim in 32% of scorings of these verified answers.

## 13.4 Standard Record Format

Every dataset is converted into one standard record format (MTLJ-41), shown in {tab:record}. Operators therefore never contain dataset-specific code, and users can bring their own data by writing a loader. The model rejects an empty question, answer, or passage. The RAGTruth loader checks the file against its checksum, skips and reports malformed lines instead of crashing, and never modifies text.

Table: Standard record format (DatasetRecord) {#record}
| Field | Type | Description |
|---|---|---|
| `record_id` | string | Globally unique ID, for example `ragtruth_13122` |
| `source_dataset` | string | The originating dataset, for example `ragtruth` |
| `question` | string | The user's question |
| `context` | list of Passage | The retrieved passages, each with `passage_id`, `text`, and optional `title` |
| `answer` | string | The known-good answer that operators edit |
| `metadata` | key-value map | Source model, task, corpus version, gold-set flag, and kept annotation fields |

## 13.5 Storage Today: The Run Directory

In Senior Design I, every audit writes a self-contained directory, described in {tab:rundir}. This was a deliberate choice. Files are easy to inspect, diff, archive, and attach to a bug report, they need no running service, and they made it possible to deliver a working end-to-end audit before the database schema was designed. The response cache is a separate SQLite file, which suits a single-user, append-mostly key-value lookup.

Table: Files in an audit run directory {#rundir}
| File | Contents |
|---|---|
| `results.json` | The results: rates, intervals, tests, curves, and run metadata. Read by the CLI, the planned dashboard, and CI |
| `evaluations.jsonl` | Every scoring, one per line, including failures and verdict counts |
| `originals.jsonl`, `mutants.jsonl`, `skipped.jsonl` | What was scored, and what was skipped and why |
| `run.json` | The seed, battery, and library versions behind the mutants |
| `config.toml` | The settings the run used, rerunnable with `--config` |
| `battery.toml` | The exact operators and intensities the run used |

`results.json` holds no timestamps, so the same scores always produce identical bytes. Its `schema_version` is 1, and readers refuse other versions. A field may be added without a version bump, as long as readers ignore fields they do not know and new fields have defaults. Removing, renaming, or changing the meaning of a field requires a bump. Section 13.10 lists its fields.

## 13.6 Choosing a Database

The dashboard needs to list runs, filter mutants, and compare two runs quickly, which is awkward over directories of JSON files once there are dozens of runs and hundreds of thousands of evaluations. Senior Design II therefore adds a database that indexes and serves run data. {tab:dbchoice} records the options the team considered.

Table: Database options considered {#dbchoice}
| Option | Strengths | Weaknesses for MTLJ | Decision |
|---|---|---|---|
| PostgreSQL 16 | Relational integrity across runs, mutants, and evaluations; JSONB for flexible operator details and results; mature async driver (asyncpg); one Docker command locally; managed hosting widely available | Needs a running server | Chosen |
| SQLite | Zero setup; already used for the response cache | Weak concurrent writes; fewer types; switching later would be rework | Kept for the cache only |
| MongoDB | Natural fit for nested JSON documents | Relationships between runs, mutants, and evaluations are central and would be enforced only in code; joins for comparisons are awkward | Rejected |
| DuckDB or Parquet files | Very fast analytical queries over evaluation tables | Not a server for a web API; no multi-user writes | Possible future export format |

The team decided in September 2026 to use PostgreSQL from the start instead of SQLite, because the design already committed to it, Docker makes it a single command, and switching later would have been rework. The PostgreSQL container has run in Docker Compose and CI since Sprint 1, and the API already has a working connection and migration (a diagnostic `connection_checks` table).

## 13.7 Access Layer and Migrations

The database is reached through SQLAlchemy 2 in asynchronous mode with the asyncpg driver, and schema changes are tracked with Alembic. The course guidance discourages unnecessary database layers such as Prisma or Sequelize. The team considered writing raw SQL through asyncpg and kept SQLAlchemy for three reasons. Alembic, which needs SQLAlchemy models, generates and checks migrations so that four people can change the schema over two semesters without conflicting. A CI test already fails if the models and the migrations disagree. And SQLAlchemy Core allows plain SQL-shaped queries and bulk inserts where performance matters, so the layer adds little overhead. The ORM is used only for simple reads and writes in the API, and bulk evaluation imports use Core inserts.

The connection comes from one environment variable, `DATABASE_URL`. Inside Docker Compose it points at the `db` service (`postgresql+asyncpg://mtlj:mtlj@db:5432/mtlj` by default, with credentials overridable from `.env`). There is no remote database connection string yet. The production string for Senior Design II will be stored as a secret on the hosting platform and never committed (Section 17).

## 13.8 Entity-Relationship Design

{fig:erd} shows the planned schema (MTLJ-27). It keeps what is being audited separate from how it is audited. A corpus version groups frozen records. Each mutant comes from one record and one operator version. A judge can have several configurations, each fixing the model, the quantization, and the settings. An audit run ties together one corpus, one judge configuration, a battery, a sample count, and a seed. Each evaluation row is one judge call and points either at a mutant or, when `is_original` is true, at the original record it is compared against. Annotations from the validation study attach to mutants.

![Entity-relationship diagram of the planned PostgreSQL schema.](diagrams/erd.png){width=4.9 #erd}

## 13.9 Indexes, Volume, and Retention

The busiest queries are "all evaluations for a run," "all mutants of one operator in a run that the judge missed," and "the same mutant in two runs." The schema therefore indexes `evaluation(run_id, target_id, sample_index)` as a unique key, and `mutant(record_id)` and `mutant(operator_id)`. The `results` column of `audit_run` holds the full results document, so the profile and comparison views read one row per run instead of recomputing statistics.

The data volumes are modest. A full corpus audit with the default battery produces about 6,000 mutants (about 6.65 per record on the gold set) and about 35,000 evaluation rows at N = 5. At a few hundred bytes per evaluation, that is roughly 10 to 20 MB per run, and the mutants, which are shared between runs on the same corpus, battery, and seed, add a similar amount once. A study of a dozen runs stays well under one gigabyte, within the free tiers of managed PostgreSQL providers.

Runs are never edited after they finish. A rerun is a new run, and the run directory remains the archival copy. A database can always be rebuilt by re-importing run directories, which also serves as the backup strategy. Run directories for the final study will be archived in the repository's release assets.

## 13.10 Results File Reference

The results file is the contract between the engine, the API, the dashboard, and any CI gate, so its fields are listed here. {tab:results_run} covers the top level and the run block, and {tab:results_rate} covers each rate.

Table: Top-level and run fields of results.json {#results_run}
| Field | Meaning |
|---|---|
| `schema_version` | 1; readers refuse any other version |
| `run.judge` | The judge's name, model, and version |
| `run.dataset`, `run.n_records` | Which dataset, and how many records were used |
| `run.samples`, `run.alpha`, `run.ci_level` | N, the false-detection rate, and the interval level |
| `run.base_seed`, `run.battery`, `run.drop_repeated_doses` | How the mutants were generated |
| `run.status`, `run.reason` | `complete`, `aborted`, or `insufficient_data`, and why |
| `run.scorings` | Totals: scorings made, succeeded, failed, and failures by type |
| `noise` | The noise floor σ and how many originals it came from |
| `operators` | One entry per operator: family, crash count, repeated doses, pooled result, per-intensity results, and dose-response curve |
| `correction` | The Benjamini-Hochberg family: method, q, and number of tests |
| `variance` | The per-condition variance report: baseline and one entry per operator and intensity |

Table: Fields of each rate in results.json {#results_rate}
| Field | Meaning |
|---|---|
| `metric`, `rate` | `detection_rate` or `spurious_sensitivity`, and its value (null when nothing is testable) |
| `wilson_ci`, `bootstrap_ci`, `headline_interval` | Both intervals, and which one to show first |
| `testable`, `excluded` | The denominator, and mutants left out by reason |
| `tau`, `n_samples` | The threshold and N |
| `paired_delta`, `effect_size` | Mean drop with its interval and spread, and the drop in units of σ |
| `p_value`, `above_chance` | Exact binomial test against α, and its verdict |
| `p_adjusted`, `above_chance_corrected` | The same after Benjamini-Hochberg correction |
| `detected` or `flagged`, `penalized`, `rewarded` | The hit counts for each metric |
